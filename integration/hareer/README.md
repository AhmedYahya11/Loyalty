# Hareer ↔ Loyalty Platform — Integration Contract

**Status:** design-only (Phase 1). Nothing in the real Hareer repo is modified yet. This
folder is the contract + a runnable mock emitter + sample payloads so the integration can be
validated against the Loyalty API before touching Hareer.

> دليل التكامل بين منصة حرير ومنصة الولاء. هذه المرحلة تصميمية فقط — لم يتم تعديل كود حرير بعد.

---

## 1. How Hareer connects

Hareer (Elysia/Bun/TypeScript/Prisma/PostgreSQL) is the **event source**. It POSTs business
facts to the Loyalty API's single ingestion endpoint:

```
POST {LOYALTY_API}/api/v1/events
X-Api-Key: <loyalty account key issued to Hareer>
Idempotency-Key: <stable per-business-event key>
Content-Type: application/json
```

Hareer already has the outbound mechanisms to do this (it calls payment/delivery webhooks,
runs an SQS worker, and has crons). **Recommended:** emit **post-commit** from the relevant
service (fire-and-forget with a short retry), exactly like its existing post-commit
notifications. Durable option: enqueue to SQS and forward with a tiny relay worker (P6).

## 2. Tenancy mapping

| Hareer concept | Loyalty concept |
|---|---|
| The Hareer platform | Root **Application** `Hareer` (platform-wide loyalty) |
| A Hareer **Tenant** (partner/store) | *Optional* child **Application** under `Hareer` (only if a partner runs its own program) |
| A Hareer **User** (`User.id`, UUID, `tenantId = null`) | **Member.ExternalCustomerId** |
| IQD integer minor units | `amount` (integer passed as-is); `spendAmountPerPoint` uses the same unit |

Phase-1 default: **one `Hareer` application, platform-wide loyalty.** Customers earn no matter
which partner they buy from. Per-partner programs are a later toggle (create a child
application per tenant and send `X-Application-Id`).

## 3. Event mapping (Hareer → Loyalty)

| Loyalty event | Hareer trigger (file) | `customerId` | `sourceTransactionId` | `Idempotency-Key` | Business key (server) |
|---|---|---|---|---|---|
| `PurchaseCompleted` v1 | `handlePaymentSucceeded` (payments.service.ts) for online; COD order creation (orders.user.route.ts) | `order.userId` | `order.id` | `hareer:purchase:{order.id}` | `sourceSystem + orderId` |
| `OrderRefunded` v1 | refund success (utils/payments/refund.ts + refunds-status-checker cron) | `order.userId` | `paymentRefund.id` | `hareer:refund:{refund.id}` | `sourceSystem + refundId` |
| `CustomerRegistered` v1 | post-signup hook (better-auth.ts) | `user.id` | `user.id` | `hareer:register:{user.id}` | `sourceSystem + externalCustomerId` |
| `ApplicationLogin` v1 | post-login callback (better-auth.ts) | `user.id` | `session.id` | `hareer:login:{user.id}:{yyyy-MM-dd}` | `sourceSystem + customerId + rewardDate` |

> Phase-1 Loyalty backend implements `PurchaseCompleted` end-to-end; the others are registered
> in the roadmap (P2) and already have their contract + business keys defined here.

### PurchaseCompleted attributes

```jsonc
{
  "eventId": "<uuid, generated by Hareer>",
  "eventType": "PurchaseCompleted",
  "eventVersion": 1,
  "sourceTransactionId": "<order.id>",
  "customerId": "<order.userId>",
  "occurredAt": "<ISO-8601, payment success time>",
  "correlationId": "<order.nanoId or a trace id>",
  "attributes": {
    "orderId": "<order.id>",
    "amount": 50000,            // eligible spend in IQD minor units (see §4)
    "currency": "IQD",
    "category": "<optional>"
  }
}
```

## 4. Money & "eligible spend"

Hareer stores all money as **integer IQD minor units**. The Loyalty `amount` is passed as that
integer. Base points = `floor(amount / spendAmountPerPoint)`.

- Example: `spendAmountPerPoint = 1000` → 1 point per 1,000 IQD. An order of `50000` → **50 points**.
- **Which field is "eligible spend"?** Default: `order.payableAmount`. If you want to exclude
  delivery, use `order.subtotal - order.discountAmount`. This is a business decision — set it
  once in the emitter (`eligibleSpend(order)`), documented below.

## 5. Idempotency & correctness

- Always send `Idempotency-Key`. Hareer retries (webhook redelivery, cron re-runs) must reuse
  the **same** key so the Loyalty API returns the original request and never double-awards.
- `eventId` must be stable per business event (derive from the order/refund id), not random per
  attempt — the server also dedupes on `(application, sourceSystem, eventId)`.
- Refunds create a **compensating** reversal referencing the original order; they never edit the
  original earn.

## 6. Security

- Loyalty issues Hareer a dedicated account API key (`lk_live_…`). Store it in Hareer env
  (`LOYALTY_API_KEY`). Rotate via the Loyalty `rotate-key` endpoint; Hareer swaps the env value.
- The key is never logged. `sourceSystem` is derived server-side from the account name.
